Le point de départ

Le portfolio affiche Tailwind CSS dans ses compétences. Afficher un mot sans projet derrière, c'est une déclaration. Pour que ce soit vérifiable, il fallait une page réelle construite avec Tailwind, manipulable dans le navigateur.

Le CSS est généré par un build Tailwind réel (npm + tailwind.config.js), puis vendu localement. La démo fonctionne hors ligne, en double-cliquant le fichier.

L'objectif

Couvrir l'approche utility-first de Tailwind dans une page complète : navigation, section hero, statistiques, cartes de fonctionnalités, formulaire et pied de page. Montrer que le fichier CSS final ne contient que les utilitaires réellement utilisés.

Ce que j'ai construit

  • Navigation responsive avec menu et bouton de thème
  • Section hero avec typographie et boutons
  • Grille de statistiques en 2 puis 4 colonnes
  • Cartes de fonctionnalités avec icônes et survol
  • Formulaire de contact avec validation
  • Mode sombre via la stratégie par classe (dark:)
  • Build Tailwind réel : tailwind.config.js, src/input.css, sortie minifiée

Les difficultés

Tailwind demande de penser en utilitaires, pas en composants. La tentation est de recréer des classes sémantiques par-dessus, ce qui annule l'intérêt. J'ai préféré composer directement dans le HTML, quitte à ce que les classes soient longues.

Le mode sombre avec la stratégie par classe exige d'ajouter dark: sur chaque élément concerné. C'est verbeux, mais explicite : on voit exactement ce qui change entre les deux thèmes.

Ce que j'en retiens

Tailwind n'est pas un framework de composants : c'est un système de design exprimé en classes. La cohérence vient de la configuration, pas des composants. Et le fichier CSS final est tiny parce qu'il ne contient que ce qui est utilisé.

Et concrètement : cette démo est la preuve qu'il y a quelque chose derrière la mention Tailwind CSS dans la section Compétences de ce portfolio.
