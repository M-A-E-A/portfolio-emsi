Le point de départ

J'ai SQL dans mes compétences. Une compétence affichée sans projet qui la démontre reste une déclaration : je voulais la rendre vérifiable, avec quelque chose qu'on peut essayer soi-même plutôt qu'un paragraphe.

Le sujet avait aussi l'avantage de tenir dans la même contrainte que le reste du portfolio — HTML, CSS et JavaScript, sans serveur ni base installée. Une base de données, en général, c'est un logiciel à part ; ici elle tient dans trois fichiers.

L'objectif

Exécuter de vraies requêtes SQL dans le navigateur, et surtout rendre le chemin visible : les jetons reconnus, l'arbre syntaxique construit, puis les phases d'exécution — FROM, WHERE, GROUP BY, HAVING, ORDER BY — avec le nombre de lignes à chaque étape.

Une contrainte s'est imposée d'emblée : pas de recherche de mots-clés dans une chaîne de caractères. Une requête contient des chaînes, des commentaires, des imbrications — il fallait un vrai analyseur.

Ce que j'ai construit

  • Analyse lexicale complète : chaînes, commentaires -- et /* */, nombres, opérateurs, mots-clés
  • Analyse syntaxique descendante récursive avec priorité des opérateurs
  • SELECT : WHERE, GROUP BY, HAVING, ORDER BY, LIMIT/OFFSET, DISTINCT
  • JOIN interne et LEFT JOIN, exécutés en boucle imbriquée
  • Agrégats COUNT, SUM, AVG, MIN, MAX, y compris COUNT(DISTINCT …) et imbriqués dans une fonction
  • INSERT, UPDATE, DELETE et CREATE TABLE avec clés, contraintes et valeurs par défaut
  • Logique à trois valeurs : une comparaison avec NULL est inconnue, ni vraie ni fausse
  • Colonnes ambiguës entre deux tables jointes détectées, avec le nom qualifié proposé
  • Erreurs situées à la ligne et à la colonne exactes, avec un repère sous la ligne fautive
  • Affichage des jetons, de l'arbre syntaxique et du trace d'exécution à chaque requête
  • Annulation des modifications, réinitialisation de la base, historique des requêtes
  • Base de démonstration (étudiants, matières, notes) conservée dans le navigateur

Les étapes

  1. 1L'analyseur lexical, testé mot à mot sur des requêtes courtes
  2. 2Les expressions, de la priorité OR/AND jusqu'aux appels de fonction
  3. 3Les instructions : SELECT d'abord, puis les trois modifications
  4. 4La résolution des colonnes à travers les jointures, et la détection des ambiguïtés
  5. 5Le rendu des trois étages et l'exploration de la base

Les difficultés

Le premier vrai choix a été le périmètre. On peut « lire du SQL » avec quelques recherches de mots-clés et ça passe sur des cas simples — mais ça casse sur une chaîne contenant 'FROM', sur un commentaire, sur une sous-expression. J'ai préféré écrire le parseur, en acceptant de supporter moins de syntaxe mais de la supporter réellement.

La logique à trois valeurs a été le point le plus contre-intuitif. En SQL, moyenne = NULL n'est pas faux : c'est inconnu, donc la ligne ne passe pas le WHERE, mais NULL OR vrai reste vrai. Implémenter AND, OR et NOT correctement demande de sortir du couple vrai/faux.

Résoudre les colonnes à travers une jointure a demandé de trancher entre deux mauvaises options : deviner à quelle table appartient une colonne, ou refuser. J'ai choisi de refuser et de proposer e.id — un moteur qui devine produit des résultats faux sans le dire.

Enfin, ROUND(AVG(moyenne), 2) : l'agrégat est au deuxième niveau de l'arbre, pas au premier. L'évaluation groupe doit redescendre dans tous les nœuds, sinon elle le voit trop tard.

Ce que j'en retiens

Un message d'erreur qui donne la ligne et la colonne exactes vaut mieux que dix messages génériques. Quand l'analyseur affiche « « KEY » attendu », on corrige en une seconde ; quand il dit « erreur de syntaxe », on relit toute la requête.

Et concrètement : la section Compétences de ce portfolio affirme SQL / MySQL. Cette page est la preuve qu'il y a quelque chose derrière.
